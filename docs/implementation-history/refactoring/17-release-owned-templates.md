# Stage 17 — Package generic harness templates

Status: **planned; not implemented**. Depends on Stage 16.
Category: resource packaging; existing generator remains active until Stage 20.

## Objective

Make an installed engine release sufficient to supply the generic orchestration
and harness presentation templates. A wheel installation must not read the
producer checkout, its `.agents`, or its root instructions.

## Implementation

1. Add the small `src/specromancy_engine/resources/adapters/` resource tree
   described in Stage 16. Use separate files only for meaningful formats:
   repository-instruction envelope, thin phase-discovery wrapper, generic orchestrator,
   pipeline launch, and existing command wrapper variants. Keep command syntax
   selection and path mapping in the existing renderer; do not build a plugin
   architecture or move validation/state decisions into Markdown.
   The phase wrapper exposes validated metadata and the canonical workflow path,
   instructs the agent to load that file, and anchors relative references there.
   It contains no copied phase body or fallback procedure. Pipeline launch
   templates still embed the complete generic orchestration instructions.
2. Move the generic content of `.agents/skills/pipeline/SKILL.md` into the
   orchestrator resource. Preserve persisted-state authority, supplied run/pipeline
   identity, mutation constraints, validation, and all stop boundaries. Do not
   embed phase-specific instructions. Keep the old file untouched until cutover.
3. Load resources with `importlib.resources.files("specromancy_engine")` through
   one small internal helper. Read resource bytes/text, not assumed checkout paths;
   do not expose a temporary `as_file()` path in persisted state or action packets.
   Accept only known release resource identifiers. Consumer source paths and
   generated files cannot substitute for package resources; apply Stage 16's
   separate source-class rules rather than treating package IDs as local paths.
4. Use standard-library rendering with explicit named substitutions. Reject
   unknown or missing template fields before writes. Substitute only the template,
   never recursively interpolate user Markdown. Preserve shell placeholders such
   as `$0`, `$1`, `$2` and `$ARGUMENTS` literally where the harness requires them.
   Do not add Jinja, YAML, or other runtime dependencies.
5. Give resources stable logical source IDs and preserve their actual bytes for
   manifest hashing. Capture the package version through the existing version
   facility. Installed absolute paths must not affect generated bytes or hashes.
6. Update `pyproject.toml` package data, `MANIFEST.in`, and the precise allowlists
   in `tools/verify_distribution.py`. Ship the same resources in direct wheels and
   wheels rebuilt from sdist. Continue excluding producer workflow policy and
   generated adapters from the runtime wheel.

## Intended files

- `src/specromancy_engine/resources/adapters/*`: new canonical release resources.
- `src/specromancy_engine/_adapters/adapter_sources.py` and, only if justified,
  a small sibling resource-loading module; retain the current facade.
- `pyproject.toml`, `MANIFEST.in`, `tools/verify_distribution.py`.
- `tests/packaging/test_distribution.py`, `test_consumer_roots.py` and focused
  adapter tests for resource loading/interpolation.
- Relevant installed-resource sections of `docs/reference/contracts.md` and
  `docs/guides/distribution-verification.md`, describing packaged assets without
  claiming the not-yet-switched generator is active.

## Verification

After the dedicated editable install required by Stage 16:

```sh
python -m unittest tests.packaging.test_distribution tests.packaging.test_consumer_roots tests.engine.unit.test_adapters
python -m unittest discover
specromancy adapters generate --check
git diff --check
```

Add meaningful cases for installed-resource availability outside the checkout,
missing/unreadable resources, literal user braces/dollar signs, and missing
template fields. Verify that a rendered phase wrapper references its canonical
source without copying its body and that a launch skill retains orchestration.
Use the existing pinned build tooling to inspect wheel/sdist
contents; do not introduce a new build stack. Full clean-consumer generation
through installed artifacts is the Stage 21 integration gate.

## Exit criteria and limits

- [ ] Both distribution forms include exact template bytes and no producer policy.
- [ ] Resource access works without producer `.agents` or `AGENTS.md`.
- [ ] Generic templates contain no phase names or phase-specific approval rules.
- [ ] Runtime dependencies remain empty and Python 3.11-compatible.
- [ ] Existing generator output remains reproducible during this preparatory stage.

This stage does not scaffold consumer files, change run records, or switch the
public renderer. Keep temporary coexistence explicit; Stage 20 removes the old
inline template/source path after the new pipeline is ready.
